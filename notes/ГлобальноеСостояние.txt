Глобальное состояние - это подход к организации данных, которые нужны не одному компоненту, а нескольким частям приложения одновременно.
Состояние - это данные, которые:
 - могут изменяться со временем
 - влияют на то, что пользователь видит на экране
 - управляют поведением интерфейса
То есть состояние - это "текущая картина" интерфейса в памяти приложения.
Локальное состояние принадлежит одному конкретному компоненту.

Часто в React встречается ситуация: одно и тоже состояние нужно не одному, а нескольким дочерним компонентам. Тогда состояние переносят на их общего родителя. Это называется lifting state uo - подтянете состояния вверх.

Поднятие вверх хорошо работает, пока дерево не становится слишком глубоким.
Если хранить состояние на самом верху и передавать его вниз через props, начнутся проблемы.
Props drilling - это ситуация, когда данные приходится передавать через несколько уровней компонентов, даже если промежуточным компонентам они не нужны.

Глобальное состояние - это состояние, которое:
 - нужно нескольким частям приложения
 - используется в разных ветках дерева компонентов
 - должно быть доступно из нескольких мест
 - желательно обновлять централизованно

Оставлять состояние локальным нужно, если:
 - оно нужно одному компоненту
 - оно не требуется другим частям приложения
 - оно относится толко к конкретному UI-элементу

Поднимать состояние нужно, если оно нужно нескольким дочерним компонентам

Делать состояние глобальным, если:
 - оно нужно компонентам в разных ветках дерева
 - его неудобно передавать через props
 - оно представляет важную общую часть состояния приложения

Управлять состоянием - значит ответить на вопросы:
 - где хранить данные
 - кто имеет право их менять
 - каким способом они обновляются
 - как другие компоненты их получают
 - как избежать путаницы и дублирования

Context - это механизм React, который позволяет передавать данные через дерево компонентов без ручной передачи props на каждом уровне.
Context позволяет:
 - объявить "общее значение" выше по дереву
 - дать к нему доступ любому вложенному компоненту
 - не прокидывать props вручную через кажды уровень 

Context - это механизм доставки данных через дерево компонентов.

Контекст создаётся с помощью createContext.
	- Мы создаём объект контекста.
	- Он будет использоваться в двух ролях:
	  - как Provider;
	  - как источник значения для чтения через useContext.

Для сложных сценариев Context часто используют вместе с useState

Чтобы передать значение вниз по дереву, используется Provider.
Он “оборачивает” часть дерева и говорит:
“Все компоненты внутри могут получить это значение контекста”.

Чтобы получить значение, используется useContext.
Через контекст можно передавать:
текущее состояние;
функцию его изменения.

Ограничения context:
Ограничение 1. Все потребители контекста реагируют на изменение значения
Если значение контекста меняется, все компоненты, которые читают этот контекст, могут перерисоваться.

Ограничение 2. Context не заменяет архитектуру
Если в одном контексте хранить всё подряд:
пользователя,
тему,
корзину,
фильтры,
уведомления,
получится слишком тяжёлый и неудобный объект.
Ограничение 3. Context удобен не для всего
Он хорош для:
темы;
авторизации;
небольшого глобального состояния;
глобальных настроек.
Но при очень сложной логике одного Context уже может не хватать.

Когда Context подходит особенно хорошо
Context хорошо использовать для:
темы оформления;
текущего пользователя;
языка интерфейса;
настроек приложения;
авторизации;
корзины в небольшом приложении.

Редьюсер - это функция, которая:
 - получает текущее состояние
 - получает описание действия
 - возвращает новое состояние

Формула:
newState = reducer(state, action)


reducer
function counterReducer(state, action) {
  ...
}

Это обычная функция.
Она не знает ничего про JSX и кнопки.
Она только умеет по входным данным вернуть новое состояние.

state
Это текущее состояние.

dispatch
Это функция, через которую мы отправляем действие.


dispatch({ type: 'increment' })

Мы как будто говорим:
“Произошло действие increment, обнови состояние”.

action — это объект
Объект действия позволяет:
описывать тип события;
передавать дополнительные данные.
Например:
{ type: 'addTodo', payload: 'Купить молоко' }

Здесь:
type описывает, что произошло;
payload несёт данные.

Редюсер должен быть чистой функцией.
Это означает:
 - он не должен делать побочные эффекты;
 - он не должен менять старое состояние напрямую;
 - он должен только возвращать новое значение.

useReducer особенно хорош, если:
 - состояние сложное;
 - есть много возможных действий;
 - обновления зависят от типа действия;
 - хочется централизовать логику;
 - обычный useState начинает разрастаться.

useState лучше, если:
 - состояние простое;
 - одно-два обновления;
 - логика очевидна;
 - reducer только усложнит код.

Сервис - это модуль, в котором находится логика, не связанная напрямую с JSX.
Проще говоря:
компонент отвечает за интерфейс;
сервис отвечает за действия, вычисления, работу с данными или внешними источниками.

В сервисы часто выносят:
 - запросы к серверу;
 - работу с localStorage;
 - преобразование данных;
 - бизнес-логику;


Сервис сам по себе не является глобальным состоянием.
Сервис:
 - не управляет ререндером React;
 - не хранит состояние интерфейса автоматически;
 - не вызывает обновление компонентов сам по себе.

Сервис — это помощник, который:
 - получает данные;
 - сохраняет данные;
 - трансформирует данные;
 - изолирует бизнес-логику.



localStorage хранит данные.
 React-state управляет интерфейсом.
 Для полноценной работы приложения их часто используют вместе.















Задание 1. Поднятие состояния вверх
InputWithPreview - это демонстрационный компонент, который показывает, как одно состояние используется в двух разных дочерних компотах:
	- InputField - отвечает за ввод текста
	- Preview - отвечает за отображение введенного текста

InputField - дочерний компонент.
 Value приходит извне → React полностью контролирует значение инпута
 onChange — функция-обработчик, тоже приходит извне
 Компонент не имеет своего внутреннего состояния — он только отображает и сообщает о изменениях

Preview - дочерний компонент
 Простой компонент отображения. Получает text через props и показывает его.

InputWithPreview - главный компонент
 Состояние поднято вверх (Lifting State Up) - в общего родителя
	text хранится не внутри InputField, а в родительском компоненте InputWithPreview
	Это позволяет делиться состоянием между InputField и Preview

 Однонаправленный поток данных (Unidirectional Data Flow)
	Состояние → InputField (как value)
	Изменение в инпуте → handleChange → setText
	Новое состояние → перерендер → обновление Preview

 handleChange — это функция-посредник
	Она получает событие от инпута
	Извлекает event.target.value
	Обновляет состояние через setText


Задание 2. Context для темы

createContext — создаёт новый контекст
useContext — хук для чтения значения контекста
useState, useEffect — стандартные хуки
ReactNode — тип для children (может быть текст, элементы, фрагменты и т.д.)

const ThemeContext = createContext<ThemeContextType | null>(null);
 - создается "контейнер" для данных
 - начальное значение null (null ставится специально, чтобы позже проверить, обернут ли компонент в провайдере)
 - <ThemeContextType | null> — говорит TypeScript, что значение может быть либо объектом с темой, либо null.

ThemeProvider - это обычный React-компонент, который будет оборачивать другие компоненты
 - useState<Theme>('light') — создаёт состояние темы (по умолчанию светлая).
 - toggleTheme — функция, которая переключает тему с light на dark и обратно.
 - useEffect — при каждом изменении theme добавляет/убирает класс dark у тега <html>. Это нужно, чтобы CSS-переменные и стили работали.
 - <ThemeContext.Provider>: Он "публикует" значение { theme, toggleTheme } вниз по дереву компонентов. Все компоненты внутри этого провайдера смогут читать эти данные без передачи через props.

Кастомный хук useTheme:
 - Это удобная обёртка над useContext(ThemeContext).
 - useContext(ThemeContext) — читает ближайшее значение контекста сверху.
 - Если контекста нет (компонент не обернут в ThemeProvider), выбрасывается понятная ошибка.

ThemeSwitcher():
 - useTheme() вызывает наш кастомный хук.
 - Получаем объект { theme, toggleTheme } через деструктуризацию
 - При нажатии на кнопку вызывается toggleTheme() → меняется состояние в ThemeProvider → происходит перерендер всех компонентов, использующих useTheme().

ThemeDisplay():
 - Здесь мы берём только theme, чтобы просто отобразить текущую тему

Как всё работает вместе (поток данных)
 <ThemeProvider>
  <ThemeSwitcher />
  <ThemeDisplay />
</ThemeProvider>

 - ThemeProvider создаёт состояние theme и функцию toggleTheme.
 - Через Provider эти данные становятся доступны всему дереву внутри
 - ThemeSwitcher и ThemeDisplay через useTheme() подписываются на эти данные
 - При нажатии кнопки:
	- Вызывается toggleTheme()
	- Меняется theme в useState
	- React перерисовывает все компоненты, которые используют useTheme()
	- useEffect обновляет класс dark на <html>

Задание 3. useReducer для списка задач

Хук useReducer — мощный инструмента React для управления сложным состоянием.

TodoReducer - это чистая функция, которая принимает:
 - state — текущее состояние (массив задач)
 - action — объект, описывающий, что произошло

	1. case 'add'
	 - Создаём новый массив (...state)
	 - Добавляем в конец новую задачу
	 - Date.now() — генерируем уникальный id
	 - completed: false — новая задача по умолчанию не выполнена

	2. case 'toggle'
	 - Используем map() — возвращаем новый массив
	 - Находим задачу по id
	 - Если нашли — создаём копию объекта и переключаем completed
	 -...todo — spread-оператор (создаёт копию объекта)

	3. case 'remove'
	 - Используем filter() — возвращаем новый массив без удалённой задачи

	4. default — важная защита: если пришёл неизвестный тип действия — возвращаем состояние без изменений.

TodoApp:

	- useState('') — управляет текстом в поле ввода (простое состояние)
	- useReducer(TodoReducer, []) — управляет всем списком задач
		- Первый аргумент — редьюсер
		- Второй аргумент — начальное состояние ([])

	- dispatch — это специальная функция, которую возвращает useReducer.
	Мы вызываем её так: dispatch({ type: 'add', payload: text })Это как "отправить сообщение" редьюсеру: "Эй, произошло действие add, вот данные".

Как работает взаимодействие

 - Пользователь вводит текст → setText() обновляет локальное состояние
 - Нажимает "Добавить" → handleAdd() вызывает dispatch({ type: 'add', ... })
 - useReducer вызывает TodoReducer с текущим состоянием и действием
 - Редьюсер возвращает новый массив задач
 - React перерисовывает компонент с обновлённым todos

То же самое происходит при клике на задачу (toggle) и кнопке "Удалить".


Задание 4. Сервис для хранения пользователя

Мы создаём систему авторизации (имитацию), где:

 - Данные пользователя хранятся в localStorage (сервис)
 - Глобальное состояние пользователя доступно через Context
 - Компонент UserProfile может читать и изменять пользователя без передачи пропсов

1. userService.ts — Сервис
Сервис - это обычный JS объект, который содержит бизнес-логику, не связанную с React. Нужен для того, чтобы отделить логику работы с localStorage от React-компонентов.
 - getUser() - читает пользователя из хранилища
 - saveUser(user)- сохраняет пользователя
 - removeUser() - удаляет пользователя

2. AuthContext.tsx — Контекст + Провайдер
 - useState(() => userService.getUser()) — правильный способ инициализации из внешнего источника (выполняется только один раз).
 - login и logout — функции, которые обновляют и localStorage, и состояние React.
 - useAuth() — удобный кастомный хук с защитой (throw error, если забыли обернуть в провайдер).

3. UserProfile.tsx — UI-компонент

 - useAuth() получает { user, login, logout } из контекста
 - Локальное состояние nameInput используется только для поля ввода
 - В зависимости от того, есть ли user, показывается либо форма входа, либо информация о пользователе

Как всё работает вместе (поток данных)

 - При загрузке приложения AuthProvider читает пользователя из localStorage через сервис.
 - UserProfile через useAuth() получает текущего пользователя.
 - Пользователь вводит имя → handleLogin() вызывает login(name)
 - login():
	 - Создаёт объект пользователя
	 - Сохраняет его через userService.saveUser()
	 - Обновляет состояние setUser()

 - React перерисовывает UserProfile, теперь показывается блок приветствия.
 - При выходе (logout) очищается и localStorage, и состояние.
